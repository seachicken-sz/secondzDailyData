# Radio on-air capture
GAS dispatches capture-radio-onair.yml on main; no cron. Configure RADIO_WEB_APP_URL and RADIO_SYNC_TOKEN secrets.
The GAS endpoint accepts POST JSON action/token: list returns items; upsertOnair accepts run_id, run_url, station_id, target_date, fetched_count, items; recordFetchLog accepts run_id, run_url, station_id, target_date, status, error_message.

## Batch sync v1
The list response advertises batch_version: 1 only after both new authenticated actions are deployed.
upsertOnairBatch and recordFetchLogsBatch accept {entries:[...]} with legacy action payloads (no token inside entries).
Both return {ok:true,results:[{station_id,target_date,ok:true|false,error?}, ...]} in input order. Each entry must be independently validated; failed entries must not stop the rest. Preserve onair_id deduplication and deduplicate fetch logs by run_id/station_id/target_date/status before enabling retry. Existing upsertOnair records success logs; recordFetchLogsBatch receives error/skipped logs only.
Without capability advertisement the client uses the old actions after collection, catching each sync failure independently. Batch mode retries transient errors up to three attempts. No batch retry should be enabled until GAS idempotency is verified.
Pending payloads are checkpointed in radio-recovery/pending.json. Private repositories only upload this file on failure for 3 days; public repositories deliberately do not upload song data. The runner's temporary files disappear after the job. To replay an authorized local copy, node scripts/capture-radio-onair.js --resume path/to/pending.json with batch v1 enabled and GAS credentials in environment. Do not commit recovery files. Success and failure counts distinguish capture from sync.
JFN nine stations have passed live collection. NACK5 and TOKAI RADIO collectors are implemented from verified diagnostic DOMs, pending live capture validation. NACK5 uses public date-specific HTML; TOKAI RADIO uses the public date selector. Both validate row dates and wait for stable rows. Alpha-station collector uses the public previous-day controls, verifies the displayed broadcast day, reads direct artist text and converts 00:00–04:59 to 24:00–28:59. Live validation pending. Other collectors are not implemented yet. Confirm permission for collection/storage, data completeness and terms before scheduling. No public redistribution.

## Proposed CROSS FM hourly checkpoint (not deployed)
Use a dedicated GAS sheet radio_hourly_fetch_state keyed by station_id, target_date (calendar JST), target_hour (00–23). Columns: station_id, target_date, target_hour, status, fetched_count, matched_count, last_attempt_at, last_success_at, run_id, error_message. Status: success, empty, error, possibly_truncated. A result is valid only if its selected date/hour, heading, table headers and row hours agree. A valid header-only table is empty, not an error. Do not mark a potentially truncated result complete; ten rows alone does not prove completeness.
GAS list should advertise hourly_version:1 and return pending hours within lookback_days, excluding future and current incomplete hours. Recheck recently closed hours (proposed two hours) for late publication; retain failure state for retry. On first run backfill within a bounded request budget (proposed 16 hours/run); prioritize recent hours and failed/unattempted older hours fairly. Sequential requests with at least 4 seconds between searches, stop on 401/403/429. Confirm source permissions before enabling.
Add authenticated batch action upsertOnairHourlyBatch with entries containing station_id, target_date, target_hour, fetched_count, items, run_id, run_url. Permit fetched_count=0 only for explicitly verified empty hourly results. Validate timestamps belong to that calendar hour; use existing onair_id dedup; write songs first, then successful checkpoint, retry idempotently. Failed entries must never advance the checkpoint. Existing daily batch protocol remains unchanged. No sheet or GAS mutation in this change.
